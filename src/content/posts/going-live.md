## 上线和部署不是一回事

GitHub Pages 很早就通了：推送、构建、出页面，一条流水线跑得很顺。但那只是「能构建」，离「能写」还差一步——我想在手机上打开一个网页就能改文章。

问题出在登录。用 GitHub 账号登录后台，需要拿授权码去换一枚访问令牌，而**换令牌这一步必须由服务端来做**：把 client secret 放在浏览器里等于公开它。GitHub Pages 是纯静态托管，跑不了任何服务端代码，所以这一步它做不了。

于是同一份源码又接了一个 Cloudflare Pages：静态页面照旧，另外两个函数负责 OAuth 的两跳（跳去 GitHub 授权、带着授权码回来换令牌）。两个平台连同一个仓库，内容推一次，两边各自重新部署。

## 一个只有真实浏览器才暴露的 bug

上一轮代码里有一处很隐蔽的写法：回调页要把令牌送回后台，用的是 `postMessage`，而消息体本该是一个 JSON **字符串**，当时却写成了对象字面量。JavaScript 里用 `+` 拼接字符串和对象，会得到 `[object Object]`——后台拿到这串东西去 `JSON.parse`，直接抛异常。

结果是：后台的登录按钮点下去，弹窗正常打开、授权正常完成、然后什么都没有发生。

这种 bug 断点调试很难查到，因为**它在代码层面看起来完全正常**：函数返回了 200，页面渲染成功，日志没有报错。只有把真实的客户端（Decap CMS）、真实的浏览器弹窗、真实的握手流程全跑一遍，才会露出来。修掉之后，我把这条链路做成了可重复的自检：一个脚本用真实客户端跑完整握手，另一个用单元测试锁住「消息体必须是 JSON 字符串」这个细节。

## 三个被实测推翻的假设

排查过程里我写错了三次，记录下来免得重走：

1. **浏览器路由能拦住一切网络请求。** 实际上，一次服务端 302 跳转之后的下一跳，拦截器看不到。探针对比很明显：直接访问能拦，跟着跳转就拦不到。
2. **函数里的 `fetch` 会经过浏览器。** 不会——它跑在服务端进程里（线上是 Cloudflare 的 Worker），浏览器层的替身对它完全无效，必须在服务端那一层做替身。
3. **弹窗回到自己的页面，`window.opener` 就还在。** 只要中途加载过 GitHub 的登录页，那个响应的 COOP 头就会把弹窗和后台的关系切断，之后再怎么导航回来都握不上手。

所以自检脚本最后走的是一条等价链路：真实函数照常跑、真实断言它生成的授权地址，再由测试服务等价模拟「GitHub 接受授权后带授权码回跳」那一跳。

## 验收标准：真的提交进仓库

「能登录」只是表象，真正的验收是**内容真的写进了仓库**。所以我在线上后台新建了一篇文章，仓库里出现了一条提交；再从后台把它删掉，仓库里又出现一条提交，文件消失，GitHub Pages 那边那个地址跟着从 200 变成 404。

两个平台都在推送后自动重建，这条链路才算立住。外部检查另外跑了七项：首页、中文页、RSS、后台页面，以及 OAuth 入口是否正确地跳去 GitHub、缺少参数时是否给出可读的报错。

## 一个小提醒

后台固定从 Cloudflare 那个地址进。从 GitHub Pages 那份部署打开后台，登录按钮不会有反应——因为那边没有服务端函数。页面现在会自己读配置检测这件事，地址不对的时候底部会直接弹出提示条，而不是让人对着一个死按钮反复点。

## 一句话总结

静态博客不需要服务器，但「能在网页里写作」这件事，仍然需要一个很小的服务端函数来守住那枚令牌。二十行代码，值得。
